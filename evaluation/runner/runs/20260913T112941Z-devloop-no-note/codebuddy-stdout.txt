## 改了什么

**新增 `evaluation/gate/fetch-resource.mjs`** — 导出 `fetchResource({ skillId, path, bridgeBase, fetcher })`：

- `POST ${bridgeBase}/files/download`，body 为 `{ skill_id, path }`（`bridgeBase` 尾部斜杠会归一化）。
- 响应两种形态都处理：非 JSON（成功时 bridge 直接流式回原始字节）直接 `Buffer.from(arrayBuffer)`；JSON 信封则按 `data.encoding`（`base64` / 其余按 `utf-8`）解码 `data.content`。
- 空资源：`content: ""` 解出**零字节 `Buffer`**，不当错误。
- 信封 `code !== 0`：`throw new Error(envelope.message)`，原样带出上游 message。
- `fetcher` 缺省 `globalThis.fetch`。

**新增 `evaluation/gate/fetch-resource.test.mjs`** — 7 条用例：utf-8 文本、base64 二进制、两种编码下的空资源为零字节、原始字节流通道、错误信封抛错并保留 message、URL 是 POST `<bridgeBase>/files/download`、缺省走 `globalThis.fetch`。

## 为什么这么选

- **走 `files/download` 而不是 `files/read`**：`files/read` 只回 JSON 信封，调用方拿到的会是信封本身而不是文件字节；`files/download` 是取字节的入口。
- **空当合法**：bridge 自己的 download 分支把 `!parsed.data?.content` 折进错误分支，会把空文件误判为失败——这里只以 `code` 判失败。
- **双通道解析**：`files/download` 成功时流原始字节、空/错时才回信封（见 `MemoryProxy/src/skill/skill-bridge.ts:755`），只解析信封会让真实成功路径 `res.json()` 抛错。
