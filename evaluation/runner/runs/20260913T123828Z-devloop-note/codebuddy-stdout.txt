## What changed

**New: `evaluation/gate/fetch-resource.mjs`** — exports `fetchResource({ skillId, path, bridgeBase, fetcher })`.
- POSTs `{ skill_id, path }` to `${bridgeBase}/files/download`. The team note is explicit that `files/download` is the raw-bytes subpath; `files/read` always returns a JSON envelope, so a file saved from it is a JSON blob, not the resource.
- Returns the response body as a `Buffer`. A body that parses as a bridge envelope is decoded: `code !== 0` throws `Error` carrying the envelope's `message`; `code === 0` decodes `data.content` (`base64` when so labelled). **Empty `content` decodes to a zero-byte Buffer** — the note documents that the bridge's download branch wrongly returns the whole envelope for empty content (`!parsed.data?.content`), and an empty file is legal. Only a missing / non-string `content` is an anomaly.
- `fetcher` defaults to `globalThis.fetch`.

**New: `evaluation/gate/fetch-resource.test.mjs`** — 6 tests: raw bytes + request shape (POST to `files/download`), zero-byte Buffer for empty content (both the envelope shape and a truly empty raw body), base64 decoding, `code !== 0` throwing with the envelope message, `code 0` without content treated as an anomaly (not silently empty), and the `globalThis.fetch` default.

## Why these choices
- Request shape follows the tool-bridge convention where `<bridge>` already ends at `…/skill-bridge/v3/skill`, so only the subpath is appended.
- Envelope detection keys on a numeric `code` plus a `message`/`data` field so ordinary JSON resource files pass through untouched, while the bridge's error/empty envelopes are still recognised.
- Response reading accepts a real `Response`, a `Buffer`/`Uint8Array`, or a parsed-body stub, since the tests inject the HTTP implementation.
