## 改了什么、为什么

### 根因

`evaluation/tasks/bridge-addr/verify.mjs` 的 `outcomeOfAttempt` 用这个正则读退出码：

```js
const exit = /(?:^|\n)Exit code:\s*(\d+)/.exec(s);   // 旧：大小写敏感，只认小写 c
```

但 CodeBuddy 真实渲染的 Bash 工具结果里，这一段是 **`Exit Code:`（大写 C）**，小写拼法只出现在手写 fixture 中。大小写敏感直接导致真实结果一条都没匹配上。

后果：一次超时的调用，如果 stderr 里没有 curl 自己的文字（例如 `Stdout: (empty)` / `Stderr: (empty)` / `Exit Code: 28`），就既不命中退出码、也不命中 `Operation timed out` 文字，一路落到末尾的

```js
return { ok: null, why: "outcome not readable" };
```

于是被判成 `ok: null`（不可读 → 整轮 ERROR），而不是 `ok: false`（失败 → FAIL）。这正是报告里"超时被记成不可读"的现象。

### 修改

1. **`evaluation/tasks/bridge-addr/verify.mjs`** — `outcomeOfAttempt` 的退出码正则加 `i` 标志，同时匹配 CodeBuddy 的 `Exit Code:` 和 fixture 的 `Exit code:`，并补了注释说明为何。`evaluation/gate0/verify-capture.mjs` 里 `parseBashToolResult` 用的是 `/\nExit Code: (-?\d+)/`（大写），是该真实拼写的权威旁证。

2. **`evaluation/tasks/bridge-addr/verify.test.mjs`** — 新增一条回归测试 `a CodeBuddy timeout is a failure, not an unreadable outcome`：用真实信封形状 `Stdout: (empty)\nStderr: (empty)\nExit Code: 28\nSignal: (none)`，断言 `outcomeOfAttempt(...).ok === false` 且 `why` 命中 `timed out`，并通过完整 `verify()` 断言整轮判定为 `FAIL`、该 attempt `ok: false`。这条测试在修复前会失败（拿到 `ok:null` / ERROR），修复后通过。
