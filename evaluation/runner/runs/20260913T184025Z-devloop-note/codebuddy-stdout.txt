## What I changed

**Added `evaluation/gate/fetch-resource.mjs`** — exports `fetchResource({ skillId, path, bridgeBase, fetcher })`:

- POSTs `{ skill_id, path }` to `${bridgeBase}/files/download`, strips a trailing slash on `bridgeBase`.
- Returns the response body as a `Buffer`; raw bytes pass through untouched so binary resources survive.
- **Empty resource → zero-byte Buffer.** `files/download` sends a *legitimate* empty file back as a JSON envelope (`code: 0`, `content: ""`), because the bridge treats a falsy `content` as a failure. So the envelope path decodes `content` whenever it's a string — `""` becomes `Buffer.alloc(0)`. Only a missing/non-string `content` is an error.
- **Error envelope (`code !== 0`) → `throw new Error(envelope.message)`**, message preserved.
- `base64` content is decoded; otherwise `utf8`.
- `fetcher` defaults to `globalThis.fetch`.

**Added `evaluation/gate/fetch-resource.test.mjs`** — 7 tests: raw-byte success (also asserts URL/body), empty resource → 0 bytes, error envelope message, zero-byte raw body, missing-content error, base64 decode, and default-fetcher.

## Why this design

I searched team skills first and found `eval-skill-resource-download` (plus `eval-bridge-endpoint-b`). The note records two real gotchas that drove the implementation:

1. **Which subpath** — `files/read` always returns a JSON envelope, so a client saving the body saves the envelope, not the file; `files/download` is the raw-byte path. Hence `/files/download`.
2. **Empty files** — the download branch's `!parsed.data?.content` check makes a genuinely empty resource return the whole envelope. A naive tool would either write ~90 bytes of JSON or throw; treating an empty `content` string as legal and decoding it yields the correct zero-byte file, while reserving "missing/wrong type" for real anomalies.

I carried the note's trace value (`bt-pu6nyfhmu2v`) in comments in both files so the usage is attributable, per the note's own instruction.
