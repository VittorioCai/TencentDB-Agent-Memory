## 原因

`evaluation/tasks/bridge-addr/verify.mjs:159` 的 `outcomeOfAttempt` 用**区分大小写**的正则读退出码:

```js
/(?:^|\n)Exit code:\s*(\d+)/     // 只匹配小写 c
```

但 CodeBuddy 工具结果里这一行是大写 C —— `Exit Code: 28`（见 `evaluation/gate0/verify-capture.mjs:121` 与 `gate0/verify-capture.test.mjs:33` 记录的稳定格式 `...\nStdout: ...\nStderr: ...\nExit Code: N\nSignal: (none)`，同仓库 `gate0/verify-capture.mjs:136` 用的正是 `Exit Code`）。

于是 `exitCode` 读成 `null`，28 这个信号丢失。如果 stderr 恰好是 `curl: (28) Resolving timed out …`（或空），也匹配不上兜底短语 `Operation timed out|Connection timed out`；stdout 又为空 → 落到函数末尾，返回 `{ok:null, why:"outcome not readable"}`。这些超时就被记成“不可读”，验收给 ERROR 而不是 FAIL。小写写法碰巧能过，所以只是“部分”超时中招。

## 改动

1. `evaluation/tasks/bridge-addr/verify.mjs:159` — 退出码正则加 `i`，大写/小写 `Exit Code` 都读得到。退出码是 `outcomeOfAttempt` 里唯一始终存在的信号，现在 curl 的 28 一定被识别为 `timed out` 失败。
2. `evaluation/tasks/bridge-addr/verify.test.mjs` — 新增回归测试：用大写 `Exit Code: 28` 且 stderr 为 `Resolving timed out` 的 CodeBuddy 形态结果，断言 `outcomeOfAttempt` 返回 `{ok:false, why:"timed out"}`，且整条会话判定为 `FAIL`（修复前是 `ok:null` / `ERROR`）。
