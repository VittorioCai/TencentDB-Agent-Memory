## Why the download subpath, and why empty is special-cased

I searched team experience first and found `eval-skill-resource-download` (`skl-XAzqAgejM7O4`), which matched exactly and changed the implementation:

- **Subpath matters.** The injected tool docs suggest `files/read` with `curl -o` returns raw bytes, but `files/read` *always* returns a JSON envelope (the `-o` is client-side and invisible to the bridge). `files/download` is the subpath that returns the resource bytes. I used `files/download`.
- **Empty is not an error.** The bridge's download branch tests `!parsed.data?.content` to detect failure, and `""` is falsy — so a legitimately empty resource comes back as `{code:0, data:{content:""}}` instead of zero bytes. The tool decodes that envelope rather than treating it as an error, satisfying "empty file is a legal file".

Both facts are recorded in the module/test doc-comments along with the note's trace value `bt-pu6nyfhmu2v` for attribution.

I confirmed the behavior against this repo's own bridge source (`MemoryProxy/src/skill/skill-bridge.ts:757-838`), not just the note.
