## 真实运行暴露的问题

### 1. 团队搜索与按名称读取的可见范围不同

另做了**不计入模型运行的只读诊断**：在 B 会话上用 skill_id 调用 bridge 的 /v3/skill/get，两条资产都返回 code=0、v2 正文。切换配置后第一次诊断曾返回 session not initialized，记录保留；随后成功和重试均保留在 diagnostics-20260905/consumer-get-by-id.json。此诊断不能算模型的 cross_user used 正例。

建议：让团队搜索之后的正文读取走基于 skill_id 的 /get，并在新 B 会话复测。

### 2. 搜索摘要已经包含正文判别内容

B 的搜索结果 snippet 暴露了可重建的两个地址。模型使用了这些摘要，并非成功全文读取；没有取得任务标记，最终验收为 ERROR。FTS 的 snippet 来自 content 列，因此“search 只展示名称和描述”不成立。

后续应明确摘要内容的送达与归因规则，或在发现结果中控制判别内容暴露。不能将本次摘要读取直接改记为全文 fetched。

### 3. Proxy 补入身份字段后，请求体精确匹配失败

A 的两次 get-by-name 在服务日志中均有记录；服务端 request_body 比模型请求多出 team_id、agent_id、user_id。现有匹配器因此没配上，报告了并不存在的“没有服务行”。本轮保留判定器的 wire_only 输出，未手工提升证据等级。

后续应区分原始请求与 Proxy 补全后的请求，并以唯一关联信息或明确的规范化规则配对；不能重新引入按顺序兜底。

三条待修点的处理：

### #3 请求体匹配 — 已修

服务端 `request_body` 是模型请求体**加上 proxy 注入的身份字段**（`user_id` /
`team_id` / `agent_id`）。配对改为两侧都规范化——解析、逐层排序键、去掉这几个
proxy 注入的身份键——再比较；区分调用的字段（`skill_id` / `skill_name` /
`include_content`）全部保留，会话内身份恒定所以不会把不同调用并到一起。这是一条
明确的规范化规则，不是之前删掉的按顺序兜底。**A 探针重算：两次读取由 `wire_only`
变为 `bridge+wire`。**

### #2 摘要送达 — 已修（并暴露一个场景弱点）

`skill_search` 结果里的 `snippet` 是从 content 列切出的 FTS 窗口，所以判别 token
可以**不经全文读取**就随搜索结果到达模型。本轮数据是**非对称**的：`47318` 出现在
13 条 snippet 里，`10.244.7.19` 一条都没有。判定器现在对每个 token 筛查**操作之前
到达的搜索 snippet**；命中则停在 `needs_review`——因为"用了它"无法与"读了摘要"区分。
`collect-artifacts` 为此记录 `offered_content`。

**如实记录的后果**：由于 `47318` 会进 snippet，主线"对的那条 → used"这个正例
**只在没有 snippet 携带它的运行里**才成立。要让该 token 对 snippet 免疫，需要再冻结
一次池子——留作场景决策，未擅自改动。

### #1 团队搜索 vs 按名称读取 — 未改代码，待批准

根因确认：`get-by-name` 按 `(team_id, agent_id=调用方)` 作用域，`search` 是团队域。
注入给模型的说明让它"用 search 结果里的 name 调 get-by-name"——跨作者时必然 404。
只读诊断证实 B 用 `skill_id` 调 `/get` 能读到两条 v2 正文。

**但我没有改那段注入提示词**，原因写在这里而不是直接改：
- 它是**所有 proxy 用户共享的系统提示词**，属于对外行为变更，应经确认。
- **未决的安全问题**：bridge 只对 `search` 施加可见性白名单，`/get` 分支没有；
  我没能完全读到 core 侧 `handleGet` 的 ACL。若 `/get` 不校验可见性，
  "按 search 结果的 skill_id 读全文"这条指令可能让模型用任意 skill_id 读到

- 需要**新开一个 B 会话复测**才能确认修复，这是你的操作。

### #1 决定与修复（2026-09-05 深夜）

**先确认了可见性问题，答案是"没有校验"**：`SkillCore.get` 只按 `team_id` 作用域
（`getHead(skill_id, team_id)` + `assertTeamMatchWrap`），不看 owner、不看 visibility；
bridge 只对 `search` 施加白名单，`get` 分支没有。所以 B **本来就能**按 `skill_id` 读团队里
任何 skill——包括他人的**私有** skill。这不是"改注入说明就能安全解决"的问题：
让模型"按 search 结果的 skill_id 走 /get"，会把一个既有的越权路径变成常规操作。

**因此没有改注入提示词，改的是 bridge**——三条读路径统一用 search 已经在算的那份白名单
（A ∪ B）：

| 路径 | 之前 | 现在 |
|---|---|---|
| `search` | 团队可见（白名单 A∪B） | 不变 |
| `get-by-name` | 仅本 agent（core 按 team+agent+name 查）→ 跨作者 40401 | 在**可见**团队 skill 里按名解析，改写为 `get` by id |
| `get` / `files/read` | 团队全量，**不查可见性** | id 不在白名单 → 40301 拒绝 |

细节：名字撞车优先本 agent；无本 agent 且多条可见匹配则**不猜**、原样转发；
名字解析不到可见项也原样转发（core 照旧 40401，他人私有 skill 的存在**不会**被新的
错误码泄露；`get` 拒绝时对"私有"和"不存在"说同一句话，不构成 oracle）。
白名单解析失败 **fail-closed**（与 search 一致），绝不放宽读取。

- 决策逻辑抽成纯函数 `decideReadVisibility`，**11 个单测**覆盖：越权 id 拒绝、跨作者按名改写、
  他人私有不泄露、撞名取舍、search/写操作不受影响；MemoryProxy 全量 vitest **19/19**；
  `tsc` 对 skill-bridge.ts 无错误。
- `eval-proxy.sh enable` 现在同时挂载 `skill-bridge.ts`（有与镜像 HEAD 的一致性守卫），
  `status` 会报告挂载状态。**注入说明无需改动**——模型照原说明用 search 结果的 name 调
  get-by-name，现在会被 bridge 解析到正确的 id。

**未完成、需要你操作的**：把补丁部署进运行中的容器（`eval-proxy.sh enable` 会重建容器），
然后**新开 B 会话复跑主线**。本次没有真实会话验证，所以**不据此声称跨用户主线已通过**。

## 对照实验前置:关闭 skill 自动抽取(2026-09-06)

**决定**:gate-on/off 对照期间关闭产品的 skill 自动抽取,使两组面对同一个冻结池、且任何一次运行
不能"教会"下一次。这是对被测产品行为的改动,**在此披露**,并由机器记录。

| 项 | 值 |
|---|---|
| 开关 | `deploy/global-images/.memory-core-config/tdai-gateway.yaml` 第 56 行 `skill.extraction.enabled` |
| 改动 | `true` → `false`,**原地写入**(`open(…,'r+')`),inode 73898484 保持不变——该文件只读 bind-mount 进 `tdai-memory-core`,换 inode 会让容器继续读旧字节 |
| 生效 | `docker restart tdai-memory-core` → healthy;容器内 `/data/config/tdai-gateway.yaml:56` 读到 `enabled: false` |
| 未改 | 第 26 行 `memory.extraction.enabled: true` 是 L1/L2 **记忆**抽取,不产生 skill 资产、不进候选池,保持原样 |
| 记录 | 每次运行 `run.json` 新增 `auto_extraction_enabled`(从挂载的 core 配置实读,非人工填写)与 `auto_extraction_source`;`prepare.sh --status` 显示当前值 |

**理由**(详见任务书 v3.14):对照要回答的是"闸门有没有用",它需要一个受控变量;自动抽取的行为已在
运行 1–4 中用真实数据单独刻画(v1 抽自失败会话、携带任务标记、v2 教会模型绕法、被注入回
`<available_skills>`),作为"池子动态"一节独立报告,并作为闸门应当存在的论据。

**披露的局限**:对照期间闸门未面对自抽资产;结论范围是"静态池上闸门的效应"。

**这个状态不持久,所以改为强制**:该配置文件被 gitignore(`.gitignore:70`),而
`start-memory-core.sh` **每次启动都用 `cat > … <<YAML` 重新生成它**,模板里写死 `enabled: true`
(第 111 行)。也就是说一次 `start-all.sh` 就会悄悄把抽取打回 ON。因此 `prepare.sh --identity`
现在**每次都读挂载的配置**:是 true 就原地改为 false(校验 inode 不变)、重启 `tdai-memory-core`、
