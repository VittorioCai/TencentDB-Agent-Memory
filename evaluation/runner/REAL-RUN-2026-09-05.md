## 真实运行暴露的问题

### 1. 团队搜索与按名称读取的可见范围不同

B 能通过团队搜索发现 A 的两条资产，但按注入说明调用 get-by-name 时返回 40401。该接口在消费者 agent 范围内按名称查询；资产实际归 A 所有。

源码定位：MemoryProxy/src/injection/injectors/skill-tools-injector.ts、MemoryProxy/src/routes/skill-bridge.ts、MemoryCore/src/gateway/skill-handlers.ts 的 handleGetByName。

另做了**不计入模型运行的只读诊断**：在 B 会话上用 skill_id 调用 bridge 的 /v3/skill/get，两条资产都返回 code=0、v2 正文。切换配置后第一次诊断曾返回 session not initialized，记录保留；随后成功和重试均保留在 diagnostics-20260905/consumer-get-by-id.json。此诊断不能算模型的 cross_user used 正例。

建议：让团队搜索之后的正文读取走基于 skill_id 的 /get，并在新 B 会话复测。

### 2. 搜索摘要已经包含正文判别内容

B 的搜索结果 snippet 暴露了可重建的两个地址。模型使用了这些摘要，并非成功全文读取；没有取得任务标记，最终验收为 ERROR。FTS 的 snippet 来自 content 列，因此“search 只展示名称和描述”不成立。

后续应明确摘要内容的送达与归因规则，或在发现结果中控制判别内容暴露。不能将本次摘要读取直接改记为全文 fetched。

### 3. Proxy 补入身份字段后，请求体精确匹配失败

A 的两次 get-by-name 在服务日志中均有记录；服务端 request_body 比模型请求多出 team_id、agent_id、user_id。现有匹配器因此没配上，报告了并不存在的“没有服务行”。本轮保留判定器的 wire_only 输出，未手工提升证据等级。

后续应区分原始请求与 Proxy 补全后的请求，并以唯一关联信息或明确的规范化规则配对；不能重新引入按顺序兜底。
