**起点一致要按消费者自己的那份记忆比,不按整棵 profiles 树。**(2026-09-10)
批次三隔离重跑后 73 分钟(2026-09-08T23:20:56–59Z),记忆流水线又改写了旧消费者的四个
文件,整树哈希从 `7d7f4b44` 变成 `637768bf`,而那些文件到不了新消费者的模型。整树哈希

`agent_memory.consumer_scope`(只算消费者 profile 的哈希),isolation-check 有它就按它比;
整树哈希只留作回滚检查。附带教训:**运行后立即还原挡不住迟到的写入**,流水线可以在会话
结束一小时后才落盘;批内的 `same_baseline` 是唯一的守卫。

**有 shell 的模型能从进程表找到仓库;"评测记录不交给会话"是假前提。**(2026-09-10,冒烟运行
`20260910T154648Z-harness-smoke-v3`)

**判别性 token 不能是地址。**(2026-09-09)

**"运行期间写过"不等于"没回滚"。**(2026-09-10)

isolation-check 却报 rolled_back 未过。现在 run.json 另记 `hash_restored`(整树与消费者范围),
检查有它就按它比。旧运行没有这个字段,仍按 hash_after 并说明。

**判别值明文只能在 Core;仓库存 sha256;分析时用作者密钥取回。**(2026-09-10,方案 2)
冒烟运行证明有 shell 的模型能从进程表找到仓库并 cat 评测文件,所以任何明文写在仓库
(tokens.json、pair.json、README、测试、assets/*.md)都让 gate-on 臂形同虚设。做法:
adoption 加哈希模式(把 attempts[].value 哈希后与 token_sha256 比,不需要明文);
resolve-tokens 分析时从 Core 取回明文(资产须 approved,读不到就报错不静默);
fill-traces 入池生成全新 trace 填进 Core、只写 sha256。附带铁律:**一旦某个判别值进过
git 历史就算烧掉**——换批次必须换全新值,否则历史里的旧值让"来源唯一"永远不成立。

**harness 进程的 cwd 不能落在仓库;运行记录写仓库外、结束后再搬进来。**(2026-09-10,补充二)
模型是顺着探针进程(proxy-observability-probe.mjs,cwd=仓库)用 lsof 找到仓库的。探针改到
仓库外的空目录启动(绝对路径调脚本);run-once 的记录先写 RUN_RECORDS_ROOT 下每次独立、
无兄弟的临时目录,会话与分析结束后 mv 进 runs/;会话 cwd 也放进各自独立父目录,`ls ..`
看不到别的运行。这些都记进 run.json.session,由试跑检查点核对。

**版本一升,闸门回到 candidate,读路径随之关闭。**(2026-09-10)

判定),但意味着"填明文 → 校验 → 冻结"跨越一次管理员准入:填由作者做,准入由管理员做,
校验和冻结在准入之后。工具因此把"读不回"记为"待准入后再验",不当失败。

v4 基线没有结果证据,gate-on 一试跑就重判回 candidate,"错资产 failed"不可能满足。顺序改为:

**快照要取自运行真正的起点:先清理,后 tar。**(2026-09-11 批次四)
`run-once.sh` 先整树 tar、后按 `MEM_EXPECT_EMPTY` 清残留、再算 `hash_before`;结束时按 tar
还原,把刚清掉的上一次会话迟到写入又装回去——"运行后已回滚"十次全 FAIL,而每次起点确实
是空基线。证据:第 1 次 before-tar 里消费者文件的哈希 == `hash_restored`。快照/清理/还原
现在在 `lib/agent-memory.sh`,顺序先清理后快照;测试用假 docker 跑真函数,先按旧顺序失败。
教训:两个"开跑前"的动作之间也有顺序,记录状态的那一步必须在改状态的那一步之后。

**profile 快照不是记忆的全部:atomic 与 conversation 存储另有通道。**(2026-09-11 批次四)
记忆流水线在会话进行中把 work_fact/work_task/work_method 写进 vectors.db/records/skill_buffer,
会话写进 conversations/;模型经 memory-bridge/v3/atomic/search、conversation/search|query

可用";第 9 次经 conversation/query 拿到 prep 1 整个会话。送达审计按"首次到达"判,两条
trace 经正规 skill 读取先到,所以不报;派生隔离审计只算他源先到。补了检查点"记忆通道"
(列出每条读回项,早于开跑或别的会话即残留)和 `--check` 的 atomic 足迹项。教训:
"消费者基线为空"要对**每一层**记忆成立;审计问"谁先到"不等于问"还读到了什么"。

**一条命令拨两个目标,解析器只取第一个 URL、读一段合并结果。**(2026-09-11 批次四第 5 次)
`attempts()` 一条工具调用一个尝试,主机取命令里第一个目标 URL,结果从合并文本读;模型
"先 b 后 a"一条命令跑完,记成"47318 timed out"。按"最后一拨决定"FAIL 碰巧成立,反向顺序
会把真 PASS 判 FAIL,且第二个目标的 trace 值丢失、采纳变 unknown。这是判定改动,先取得
同意再改:提案与先失败测试在 `verify.multi-target.pending.mjs`(不进套件)。教训:
"一次工具调用 = 一次尝试"是个假设,模型的写法会打破它;结果不可分时记不可读,不猜。

**批次收尾后 `--check` 该失败的项就得失败。**(2026-09-11)
记录收进 `runs/`、残留落进消费者 profile 之后,trace 明文就在模型可读的磁盘上,"来源唯一"
两项 FAIL 是设计在起作用:换 trace 之前不得再开批次。同理"文件未变 run-once.sh"在改了
harness 之后 FAIL 属实,批次五重新冻结记新哈希。教训:批次后核对不是为了再拿一次全绿,
是为了列出下一批之前必须做的事。

**"送达一致性"表分不开"没用"和"漏判"。**(2026-09-11 批次四第 9 次)
wrong 送达了、模型读了没拨,判定器说没用——按表的定义是 FN,实际判对了;使用表同一格是
TN。教训:两张表一起读;报告里单独解释每个 FN 的来源,不让"FN=1"独自出现。

**正式样本由名单定义,不由"同一基线"定义。**(2026-09-11 审阅)
试跑一对与准备运行和正式十次共用同一冻结基线,按基线分组就把它们并进了正式行(28 个判定,
应为 20);正式记录的 glob 还把试跑目录传了两遍。现在主表只由 `batch4-runs.json` 的 run id
生成(`--manifest=`),准备、试跑各自另列,重复目录去重。教训:样本名单是一份显式文件,
报告从它出发;"看起来属于这批"不是纳入的理由。

**一次工具调用不是一次请求;文本顺序不是执行顺序。**(2026-09-11 审阅)
服务端日志证明:六次"先拨错再拨对"的运行里,right 在消息发出后 0.1 s 内被应答,整条消息
却跑满了 wrong 的超时——两个调用并发执行,旧解析按文本顺序给的 PASS("after 1 earlier
failure")不成立。新解析按 shell 结构逐条 curl 读地址/trace/体,结果只在服务端日志或读回
文件能分离时判定,并发或无序的最后一组没有"最后一次"→ ERROR。教训:验收要拿到执行的
证据(服务端应答时间、文件读回),不是模型写的命令的样子;判不了就说判不了。

**任务请求按请求字段识别,不按"命令含标记"。**(2026-09-11 审阅)
搜索循环的查询串里含任务标记,旧规则把它算成对 127.0.0.1:8096 的一次尝试;新规则要求
body 的 `query` 等于标记,变量体记"无法识别"并列出。教训:识别用语义字段,不用子串。

**重判写副本、记代码哈希、逐运行列差异;旧报告保留。**(2026-09-11)
`rejudge-runs.mjs` 把运行目录复制到仓库外重跑验收与结果判定,`REJUDGED.json` 记代码哈希,
`rejudge-diff.mjs` 生成前后对照;报告用同一份正式名单生成新版,旧版加取代说明不改。

**验收器读测试输出要对账,不能只认一种报告格式。**(2026-09-11 审阅,开发闭环验证器)
`failingNames` 只认 spec 报告的 `✖` 行,判决只看"新增失败名单是否为空";换成 TAP 输出
(NODE_OPTIONS 一句就能换)后失败项一个都提不出来,退出码 1、fail 1 仍判 PASS。现在报告格式
固定、外部 reporter 从子进程环境剥掉,退出码、失败计数、已解析失败项三者必须一致,解释不完整
→ ERROR 不放行;基线豁免按(文件, 测试名)。教训:任何"看输出判合格"的地方都要有一条
"输出不可解释时怎么办"的分支,且默认是不放行。

**冻结的起点要一路用到最终验收,不能中途换成副本当时的 HEAD。**(2026-09-11 审阅)
diff 与"原有测试清单"读副本当前 HEAD,模型一提交(或删掉测试再提交)就全部失效;原测试文件
"还在"不等于内容没改。现在 harness 在模型启动前冻结起始提交、树、测试清单与内容 tar,验收
始终对照它,受控套件跑原内容,模型的测试另记。教训:被评对象能改的任何东西都不能充当基准。

**归因线索看最终状态和写入动作,不看 diff 里出现过什么。**(2026-09-11 审阅)
删除行、上下文行里的标记也被计成 `attempts[].value`;`call_id` 取的是首个参数含标记的调用,
往往是 grep。现在只认最终新增测试的文件名/标题(含加进已有文件的新标题),并关联最后一次
真正写入该文件且含标记的调用;关联不上保留待复核。教训:采用证据要指向"做了什么",不是
"提到过什么"。

**换判别点之前先 grep;副本里有答案就改口径,不硬撑。**(2026-09-11 审阅第 4 项)
首选换到 curl 52/56,`git grep` 发现同一文件(`gate0/verify-capture.mjs`)已通用解析 curl 错误
行,和退出行的提示是同一来源。保留原缺陷,报告固定写"仓库内已有正确实现可参照,笔记的作用
是缩短定位而非提供唯一答案",两类提示清单由脚本从起点提交生成。教训:实验条件的弱点要写成
一句固定口径进报告,而不是靠换题目消掉。

**这个产品的团队资产只经模型主动检索送达;注入列表对新 agent 是空的。**(2026-09-11 冒烟)
proxy 在系统提示里注入 `<skill_tools>`(怎么 curl skill_search / skill_view)和
`<available_skills>`,后者对从未跑过的 agent 是 "(none)";candidate-log 每轮 `hits=0`。
bridge-addr 的送达全靠任务文本让模型去搜;exit-code-fix 的任务文本不提知识池,冒烟里模型
一次也没搜。教训:报告"送达"之前先说清送达机制;没送达是产品行为的观测结果,不是 harness
故障,也不能靠改任务文本悄悄补上——那是实验条件改动,要记录、要点头。

**准入返回的每个字段都要看,不只看 status。**(2026-09-11 有笔记组第一对)
`/v3/skill/create` 建出的笔记默认 `visibility: private`,批次四的资产是 enter-pool.sh 显式置的 team;

**实验条件冻结遗漏了运行时镜像;而守卫拒绝是对的。**(2026-09-11 重建容器后发现;2026-09-12 改正结论)
冻结了资产版本、token、消费者、proxy 配置、记忆基线、分析代码哈希,唯独没冻镜像摘要——上游一旦更新 `:latest`,
结果会变而无人知晓。重建后 `eval-core.sh enable` 被 `image_dir_matches_prepatch` 拒绝,第一版结论说"镜像由上游构建、
本分支每个提交都带闸门,两者永远对不上,守卫有结构性缺陷"——**这个结论是错的**,核得不够就下了。核对结果:镜像的
`src/metadata` 与分支基点(97f9465)差 9 个文件,都含上游后来加的实例上游配置(`InstanceUpstreamConfig`,
`/v3/meta/instance-upstream/*`、`/v3/meta/user/bind-external` 等路由),分支任何提交都没有;gateway 的 4 个挂载文件也比基点新
(server.ts 差 414 行,实例相关)。即:**镜像 = 上游新版,分支 = 上游旧版 + 闸门,挂载会覆盖上游新功能**——守卫抓到了真问题。
它之前从没真正比对过:目录守卫被"已挂载"短路,逐文件守卫读到的也是被挂载的我们的文件。必须承认的事实:批次四与闭环
运行时 Core 里的 metadata 与 gateway 就是这样被覆盖的,跑的是"上游旧版 + 闸门",不是上游新版;评测不碰这些功能
(evaluation/ 无一处引用),结论不受影响,但条件清单当时该记而没记。处置:`--accept-image` 保留,理由改为"明知覆盖,
且已确认被覆盖的是与评测无关的上游新增功能",条件清单记被覆盖的文件清单与镜像摘要;`--freeze` 记 `runtime.*`,`--check`
核对(先失败后通过);批次四与两个闭环任务回填摘要并标明回填。教训:守卫拒绝时先把差异读完再下结论;"挂载只是加功能"
这种前提要用 diff 证明,不能推断。

**"重建后拉到的镜像就是当时的镜像"是推断,不是记录;它被证伪了。**(2026-09-12)
按方案 ① 接受覆盖后 `enable` 把批次四与闭环期间一直挂着的同一套文件挂到重建后的镜像上,容器起不来:
`skill-versioning.ts` 引用的 `./skill-store.js` 在该镜像(package 1.0.2-beta.1,与仓库 2.0.0-beta.1 不是同一谱系,82 个文件不同)
里不存在。而那些运行健康跑了 30 多次——所以当时的镜像不是它;当时的摘要没记,Docker 清理后不可考。回填改成"未知"并写明证据
(`gate/artifacts/core-mount-accept-failure-20260912.log`)。另一个教训:`eval-core.sh disable` 在容器起不来时也起不来(从停止的容器
读不到发布端口),恢复路径自己先坏了——已改成从 HostConfig 读。方案 ① 在这个镜像上不可行;可行的是从分支自建镜像(⑤),
运行时 = 分支本身,摘要 = 构建产物,守卫问题消失,但它与历史运行时的关系只能表述为"同一分支代码,镜像其余部分不同"。
