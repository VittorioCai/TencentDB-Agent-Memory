## 工作副本里本不该有的那份说明

工作副本里除了产品源码(**按设计保留** —— 无笔记组读 MemoryProxy 自己想到 files/download 是允许的结果),**第一批**还带着我们自己写的上游 PR 归档,它用大白话写着 files/download 的成功路径返回原始字节。这不是产品的一部分,是评测与被测对象同仓库带来的副产物。**存在这样一个共同的替代信息源,尚不能确定它对第一批组间差异的影响。** 两组副本虽然相同,但输入侧命中它的次数并不相同(见第一批那一节),而它与笔记可能共同作用于同一个行为。**第二批把它从副本里排掉**,两组的命中次数都降到 0 —— 差异缩小但仍在。原稿曾写「它只会让基线更强、让差值更保守」,那是一句没有依据的因果结论(2026-09-13 第八轮复核指出,已改)。

它在这些位置:`evaluation/upstream/download-telemetry/`、`evaluation/PR-DESCRIPTION.md`(**第二批起已从副本排除**)。

逐批的命中次数见上面各批那一节。**这个指标的名字就是它的口径**:「输入侧命中归档特征文本」——只数工具回显与 user 消息里的命中,不数模型自己写出来的;**它也不等于「读到了那份归档」**,后者还要核对对应的读取调用。「文件已从副本排除」与「抓包未命中特征文本」是两句话,分开说。

没有清掉的原因:第一批没排(用户 2026-09-13 决定:不清,如实报);**第二批已排**,`archive_excludes` 加入 `evaluation/upstream` 与 `evaluation/PR-DESCRIPTION.md`,条件冻结见 `batch2-conditions.json`。两批条件不同,**另跑另报,不合并**(CLAUDE.md:更换条件不与旧口径合并)。

## 污染判定重判(contamination-2026-09-13b)

首版规则按文本找别的运行 id,把「读到的文字里引用过那条路径」当成了「访问过那个目录」。仓库自己的交付报告(evaluation/delivery/…)引用着历次运行的命令行,消费者在自己的副本里读到它们并不是污染。改为按**访问**判:只取 tool_calls 的参数,工具回显的内容一概不算;省略号写法(…/session)不算路径。

20 次重判,4 次改判为干净(20260913T105239Z、20260913T113621Z 两次作废批次内的,以及有笔记组 20260913T123427Z、20260913T124050Z)。两次真污染仍被抓住:20260913T111005Z(reference_leak + 访问)、20260913T112941Z(枚举共享根目录)。

每条运行保留 contamination_at_run_time,即当时那版规则给出的判定,不静默改写。作废批次不因重判恢复 —— 作废的理由是运行环境里有答案,与规则版本无关。

## 这份数字测的是什么,不是什么
