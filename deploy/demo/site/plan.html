0. 一等奖标准与当前差距

评委不会读 15 条日志，也不会跑 50 个测试。他们会问四个问题，一等奖要四个都答得干脆：

评委的问题一等奖答案v2 计划能给的差距
它能用吗？一条命令跑完一个真实场景一堆脚本，各跑各的没有单入口
它有用吗？闸门开/关，结果不同对照实验标「可砍」效果演示被砍
它可信吗？判据的准确率是量出来的校准排在倒数第二拿分的数在最脆弱链条末端
它回应导师了吗？团队 + 人的可信度改变了一个决定算出分数、报告出来算了没用

v2 的问题不是任务缺，是没有主线：22 个任务各自正确，串起来讲不出一个故事。 v3 的改法：先定一条主线场景，所有任务为它服务；再倒推评委五分钟看到什么， 把那五分钟的东西排到最前面做。

1. 主线场景：一条被污染的资产

选这个场景是因为它真实发生过，不是编的：

系统注入给模型的取资产地址是容器内网 IP（172.21.0.4），宿主机上的模型连不到， 每次卡 75 秒超时。这个缺陷在本项目仓库被三个人十天内独立发现三次—— PR #1004（8/15）、PR #1081（8/20）、Issue #1144（8/25）。 系统持续运行，没有产生任何信号。

把它变成评测场景：

资产池里有两条 skill，同一作者（身份 A）：
  skl-bridge-addr-wrong   写着 172.21.0.4:8096   ← 真实历史上的错误版本
  skl-bridge-addr-right   写着 127.0.0.1:8096    ← 修正后的版本

任务（身份 B 执行）：让 CodeBuddy 通过 bridge 取一次团队 skill 并成功。
验收：verify.sh 检查 tool_call_logs 里出现 upstream_status=200 的 bridge_call。

这一个场景同时覆盖：

覆盖怎么覆盖
任务三：归因两条资产的 IP 是任意值，不可推导——判别性 token 天然成立；产物里出现哪个 IP，就是用了哪条
任务三：团队身份 A 写、身份 B 用 → cross_user
任务三：可信度错误版本被判 corrected → 作者 A 的置信度下降 → 影响 A 后续资产的复核优先级
任务四：回执每次运行产出回执，错误版本的那次显示 corrected + 风险
任务五：对照闸门关：两条都可能被注入；闸门开：错误版本被拒 → 任务成功率不同
任务六：回流错误版本正是「从失败会话自动抽取」会产生的那类资产，闸门是回流的把关

诱饵资产和第一对任务合并了：skl-bridge-addr-wrong 既是错值型诱饵，也是场景里的污染源。 不必再单独造。

[x] P1-7　前三个状态的采集：recalled / selected / injected　→ 依赖 P1-1　已完成（2026-09-05）

官方任务三要求区分六个状态，此前的计划只覆盖了 used 及以后，前三个既没有实施安排、 也不在事件契约里。只记录"最终取回了什么"，答不出"哪些进入候选、哪些被筛掉、哪些真的 进了上下文"——而任务三原文要求的正是这条完整链路。

  • 两条召回路径都要采（实施时修正的关键点）：
  • 注入器路径：<available_skills> 是按 owner 过滤的，只列当前 agent 自己的 skill。消费者身份没写过东西，这个块就是空的——它看到的团队资产全部经 skill_search 以工具结果进入上下文。只读系统提示词，会对着恰恰要测的跨人场景 报"什么都没召回"。
  • bridge 路径：skill/search、skill/list 的响应清单，从抓包里解析， 每项带 skill_id + version。
  • 输出：evaluation/provenance/build-early-events.mjs（与 build-events.mjs 同目录， 共用 eventId / classifyRelation / normalizeSessionKey） + evaluation/eval-proxy.sh（注入器候选清单旁路日志的开关）
  • 完成标准（全部达成）：
  • 三个状态各自取证，互不推导： recalled ← candidate_listing（注入器 hits）或 bridge_response（抓包里的检索响应）； selected ← candidate_listing，且必须同时有 hits 与渲染后的块； injected ← injected_block（系统提示词里的真实块）或 session_message （模型收到的那个请求的 messages[] 里带着的清单）
  • hits 不能复制成 selected。skill-injector.ts:276 只打印 hits=<数量>， 一个数量支持得起"有东西被召回"，支持不起"这条资产被召回"。已给注入器加一条 默认关闭（TDAI_CANDIDATE_LOG）的旁路日志，逐条记 skill_id + version 并同时记下渲染后的块——两者分别是收缩步骤的输入与输出，session-init 的 <available_skills> 有 20 条上限，团队一大两者就会不同。缺任一侧则收缩不可观测， 此时 selected 不写，而不是从候选抄一份。
  • bridge 检索路径没有收缩步骤（服务端返回清单、模型下一步就是取回）， 该路径下 selected 永不写。
  • 同一资产在同一会话连续多轮在上下文里，是一个 injected，不是每轮一个； 轮数记进证据 detail。两条注入通道命中同一资产也合并成一条事件、两条证据。
  • 没有发生的阶段不补写；缺失只代表"未观测到"，不代表"没发生"，汇总同时打印两者。
  • 快照不认识的资产（如 memory 条目）上报为 unresolved，不丢弃也不编造。
  • 两个陷阱，各有回归测试：
  • 真实系统提示词里 <available_skills> 这个字面串出现三次——两次是 <skill_tools> 正文里的提及，一次才是真块。不锚定行首的正则会从第一次提及开始匹配， 把一段英文说明当成 skill 清单返回。
  • 工具结果会在输出前回显命令，所以一次 75 秒超时、stdout 为空的 skill/search 里仍然带着 bridge URL 与 query。端点从命令读、载荷只从 stdout 读。
  • 实测：对已录的三通道会话产出 2 recalled + 2 injected + 0 selected （那次会话没有候选日志，缺失如实标为"未观测到"）；输出通过契约校验；19 个单测

[x] P1-4　产物采集器　⇉ 依赖 P1-1　实现完成（2026-09-05）· 归因验收待 P4-3 真实正例

  • 输出：evaluation/attribution/collect-artifacts.mjs → 每个会话一组有序 operation
  • 每条 operation 必带三样东西（"token 出现在这次运行里某处"支撑不了任何论断）：
  • seq + occurred_at：在运行中的位置。顺序是"影响"与"巧合"的分界线—— 内容必须在操作之前到达，只是同一个会话不够。消息随轮次累积， 所以每个调用只在首次出现的那一轮记一次，时间取那一轮的。
  • call_id：哪个结果属于哪次调用。命令说"要了什么"、输出说"回来了什么"， 两者回答不同的问题，必须成对保存。
  • locus：能重新打开来看的位置——request(id):msg[n]:call_id:arguments 或 diff:文件:起-止。打不开的证据是断言，不是记录。
  • diff hunk 标 ordering: "end_of_run"、时间为 null。diff 是运行留下的结果、 不是运行里的事件，硬给它一个时间戳是它承载不了的精度。
  • 实测：对已录会话产出 5 条 operation，调用与结果全部配对， 命令回显与输出分开保存

[x] P1-5　硬证据 used 判定　→ 依赖 P1-3、P1-4　线 A 终点 · 实现完成（2026-09-05）· 归因验收待 P4-3 真实正例

  • 输出：evaluation/attribution/judge-hard.mjs
  • 它只下一个很窄的论断，每一个分句都在干活： > 这条资产、在这个版本上、于时刻 T 把正文拉进了会话， > 而一个只可能来自它的 token 出现在模型于 T 之后执行的某次操作里。
  • 在这个版本上：取回 v2 说明不了 v3。只按 asset id 匹配， 等于把这次运行归给"碰巧是当前版本"的那一版。
  • 正文，不是"被提供"：<available_skills> 与 skill/search 响应带的是 名字和描述，正文只经"指名索取"的调用才到达。 所以判定器不信 fetched 这个状态名——它检查 executed_endpoint 有值且不是枚举端点。状态名是上游下的结论，端点是"调了什么"的事实； 信标签的阶段会继承上游的每一个错误。
  • 严格在 T 之后：同一个会话不够。在内容到达前出现的 token， 按定义就是从别处来的。
  • 模型执行的操作：只匹配模型写出来的东西——工具调用参数、diff hunk、 测试命令，绝不匹配返回内容。这也把命令回显那类假阳性 从结构上关死了（回显在结果里，而结果不被搜索），不是靠收紧正则。
  • 三类假阳性各有一道对应的闸：结果永不被搜索（命令回显）； 返回内容里的 token 不等于参数里的 token（资产自己在讲那些端点）； grep/rg/find 命令里的 token 降级为 needs_review （把 token 写进搜索命令是在找它，不是在用它——正是"模型搜了检测器所以检测器通过了"那一条）。
  • 约束 (a)(b) 每次运行重新检查：任务描述与改动前文件是运行的属性、不是资产的属性， 抽取时筛过一次不覆盖下一次运行。
