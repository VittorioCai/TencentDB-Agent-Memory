资产准入闸门

团队资产在被模型读到之前，先由产品自己判定能不能用。这里是可以点开的产品，和支撑它的评测证据。

这是演示实例。交付的数字以仓库中的冻结基线和十次运行的原始记录为准，不以这台机器上的当前状态为准。 你可以在审核队列里随便点——准入、拒绝、逐条推翻纠错都可以；点乱了运行 reset.sh 十秒还原。

看产品

审核队列 →闸门对每个资产的判定和理由、被排除的证据行（不受信 / 已撤回 / 其他版本 / 无绑定 / 时间并列）、作者评估，以及人工复核：准入必须逐条点名它推翻的纠错并写明理由。 完整面板 →资产列表、技能、团队与成员。审核队列之外的部分。

看评测

第三批 off/on 对照 →规则冻结后各跑五次。两臂验收都通过；差别在首批调用——关闭时 4/5 先拨了错地址，开启时 0/5。含隔离性说明，包括那一次地址经另一条通道到达。 闸门设计与验证 →准入规则、版本与内容绑定、人工复核的边界、每一轮复审的反例与实测记录。 作者证据链 →从作者自己的记录出发的评估：引文核验、事实核验、三本账、以及资产版本 → 写入者 → 来源会话 → 操作 → 结果这条链。 执行计划与修订记录 →阶段划分、验收条件，以及每一轮改了什么、为什么改、哪些仍未解决。

一句话说清它做什么

一个团队成员写下的技能，可能是错的。产品不能因为"它在库里"就把它喂给别人的模型。

问题这里的做法
作者自己说自己对只有他人使用后的受信结果才算证据；作者不能复核自己的资产
旧结论套用到新版本判定绑定版本 + 内容哈希；改一个字，此前的准入即失效，重新回到候选
人工一句"我看过了"就放行准入要逐条点名它推翻的每条纠错并写理由；没点名的仍然生效，资产维持不通过
判定写下时证据已经变了写入同时受资产版本与证据集合约束；期间到达的新证据会让这次写入被拒、重新判定
报告说"隔离干净"其实不干净隔离失败与归因错误分开记；覆盖不足记 unknown，不记干净
